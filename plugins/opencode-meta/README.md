# opencode-meta (OpenCode v2 plugin)

Typed, read-only `opencode_meta` tool for bounded questions about current OpenCode session metadata. This is the v2 port: it no longer opens the SQLite database directly (as the v1 version did) and instead uses the v2 plugin API plus a live event index shared with `../opencode-recall-lite/session-index.ts`.

## Operations

| Operation | Source | Notes |
|---|---|---|
| `session` | `ctx.session.get` | Defaults to the calling session. Id, title, parent, project, directory, agent, model, outcome, cost, tokens, times. |
| `session_tree` | `get` + index | Parent via API; children from sessions created since indexing started. |
| `session_stats` | `ctx.session.context` | Message counts by type, assistant part types, per-tool call/error counts, cost and tokens for messages in model context. |
| `recent_sessions` | index | `directory`, `days` (default 7), `limit`. |
| `tool_usage` | `context` over one session or up to 25 recent indexed sessions | `session_id`, `directory`, `tool_name`, `days` (default 30), `limit`. |
| `capabilities` | app/location/index | Replaces v1 `schema` and `database_info`; reports index coverage and limits. |
| `message_digest` | plugin state | Digest mode for the **calling** session: `enabled: true` (with `minutes`, 5–60, default 15), `enabled: false`, or neither to see the state (interval, held count, next digest). See below. |

A separate `peer_inbox` tool reads and acknowledges the calling session's own peer inbox (see below).

## `send_message`

Cross-session messaging after Claude Code's: `send_message {to, text, delivery?}` sends plain text (up to 8,000 characters) into another session, found by session ID or by title (exact, or a fragment matching exactly one indexed session; an ambiguous title returns the candidates). By default the target receives it at its next step boundary (`delivery: "steer"`; `"queue"` waits for the target's next turn, which can be hours for a session running a long chain of subagents), framed as coming from the sending session (ID and title), with a note that it is peer information rather than user approval and cannot answer a permission prompt, plus the reply address. It never messages the calling session. A subagent's message to its own parent is held, because the subagent's final reply also reaches that parent: if the subagent calls another tool (it is still working) the message is delivered then; if its turn ends first, a foreground run's messages are merged into the parent's `subagent` tool result ahead of the final reply, and a background run's are delivered as it finishes, beside the completion notice. Held messages are never dropped (`relay.ts`). Delivery uses the public `ctx.session.prompt` and records `metadata.crossSession.from` and `.priority`.

### Typed receipts and the passive peer inbox

`send_message` takes an optional `receipt`: `{version: 1, kind, id?, work_item?, revision?, job_id?, state?, supersedes?, restrictions?, unresolved?, evidence?}`, validated at run time (the tool schema is not trusted). A malformed receipt, or a message plus receipt over 40 KiB, is refused with "Nothing was recorded or sent"; nothing is clipped. Messages without a receipt keep exactly their existing delivery.

- **Passive:** `kind: "fyi"` at normal priority, `state` absent, `"progress"` or `"completed"`, and no `restrictions` or `unresolved`. It is stored durably in the recipient's peer inbox **before** any parent relay, and nothing is prompted: no wake, steer, digest or model call, whether the recipient is idle or busy, in digest mode or not. The sender gets `{recorded: true, passive: true, delivered: false, processed: false, receipt_id, status: "pending"}`; the recipient has not read it. A resend of the same receipt stores nothing new and reports `duplicate: true` with the recipient's actual current `status`, `version` and any `read_at`. A child's FYI to its parent is stored the same way and never merged into the child's final report.
- **Everything else is delivered as before:** `kind: "actionable"`, an FYI with state `"blocked"`, `"failed"`, `"cancelled"` or `"unknown"`, any restriction or unresolved item, an urgent or downgraded-urgent priority, or an unrecognised kind or state. The receipt fields are appended to the framed text (restrictions exactly as given) and recorded in `metadata.crossSession.receipt`; the result adds `passive: false` and `routing`. Every typed receipt, whatever its route, is first stored as an immutable original (so its ID, conflict and 40 KiB checks apply before any delivery). Unless a recipient's digest holds it, it is `direct`: delivered on its own (immediately, or when the parent relay releases it) under its own manifest and stable native ID, and never joins a digest, except that a normal one the relay releases to a parent in digest mode is durably marked released (`released_at` on its `peer:state` record, no new version) and then waits for that digest like any other; until the relay chooses release or merge it is never digest backlog. A direct receipt whose manifest exists is never attempted again; a resend of the same receipt reports `duplicate: true`. An immediate attempt whose outcome is lost is reported as an error saying it is unknown and must not be resent. A relayed receipt merged into the child's final reply stays visible as `pending` in `peer_inbox`.
- The classification trusts the producer's labels. Free text marked FYI cannot be proven harmless; untyped callers keep costing their existing wakes until they adopt receipts.

Originals are immutable records `peer:event:<recipient>:<sender>:<id>`; the recipient-facing ID is `<sender>:<id>`. A receipt `id` is an idempotency key scoped to sender and recipient: the same content again is `duplicate: true`, different content is refused. A failed or uncertain storage write is reconciled by reading the same key back; a write that cannot be confirmed is reported as not recorded, never as recorded. Recipient dispositions (`peer:state:…`) and delivery manifests (`peer:batch:…`) are separate records, so reading, acknowledging, superseding and delivering never rewrite or delete an original. There is no garbage collection, expiry or total size limit. Each original is capped at 40 KiB, but the on-disk store and the server's in-memory copy grow with every distinct message, even after it is acknowledged or archived, and are all loaded again at startup. Acknowledging or archiving keeps the inbox views short; it does not free space. A sender that loops on passive reports can therefore fill the disk or memory. Watch `stored_bytes` in `peer_inbox status`. List and ack headers show at most the first 200 characters of a sender's title.

**Supersession is a view.** An FYI may list earlier FYI receipt IDs of the same sender in `supersedes`. The decision is stored inside the new original, one immutable write, so it applies to all named entries or none, also across a failed write or restart; it records exactly which predecessors it archived (the first superseder wins), so a restart derives the same `superseded_by` and version whatever the timestamps or IDs. They show as archived (`reason: "superseded"`, `superseded_by`, version raised by one so an ack from an older view conflicts; an explicit recipient disposition takes precedence) only if every one exists for the same recipient, is passive, and has the same kind, `work_item`, `revision` and `job_id`, and the new receipt names a `work_item` and `revision`. Otherwise the new report is stored uncoalesced with `supersession_applied: false` and the reason. Actionable reports never supersede and are never hidden.

**`peer_inbox`** acts only on the calling session; it has no target argument.

| Operation | Arguments | Result |
|---|---|---|
| `status` | — | Counts by `pending`, `offered`, `processed`, `archived`; passive and actionable pending; unread; delivery attempts needing attention; stored bytes; `complete: true`. Until every stored record has been read back (or when that failed) it returns only `complete: false` and why, never an empty count; `list`, `read` and `ack` then refuse, and nothing is delivered automatically. |
| `list` | `cursor?`, `limit?` (≤ 20), `status?` | Headers oldest first, with `version`, `next_cursor` and `remaining`. |
| `read` | `ids` (≤ 20, each ≤ 256 characters) | Exact originals and receipts, whole entries; the whole result, with `missing`/`remaining` descriptors, is at most 48 KiB; the rest are listed in `remaining`. Records `read_at`; reading is not processing. |
| `ack` | `items: [{id, expected_version}]`, `disposition: "processed" \| "archive"` | Per-item result; a stale version returns the current header instead. No reply, message or wake is sent. |

`offered` means a digest carrying the entry was admitted natively; only an explicit `ack` makes it `processed`. Nothing schedules a check of the inbox: a session reads it when that suits its work.

### Priority and digest mode

`send_message` takes `priority`: `"normal"` (default) for progress reports, FYI and finished work that needs no immediate action; `"urgent"` when the recipient must act now (a blocker, a failure, a decision or permission it must give, a security, data-loss or live-incident issue, or the answer to a question it is waiting on). For a recipient **not** in digest mode, priority is only recorded in metadata and nothing else changes. An urgent message must also give `urgent_reason`, one line starting with its category (`blocker`, `failure`, `decision`, `permission`, `incident` or `awaited-reply`, then a colon) and why the recipient must act now. Without a valid reason it is sent as normal, and the result says `downgraded: true` with a note. The reason is shown to the recipient as `[urgent — …]` and recorded in `metadata.crossSession.urgent`.

A session turns digest mode on for itself with `opencode_meta {operation: "message_digest", enabled: true, minutes?}`, typically a long-running controller that many workers report to, where each wake re-reads a large context. Sessions can also be listed in the plugin options (`"digestSessions": ["ses_..."]` or `{"ses_...": 20}`). A session's own `enabled: false` is remembered and wins over the options. For a recipient in digest mode:

- **Normal** messages are held. The sender gets `{delivered: false, held: true, digest: true, due_at, due_in_minutes, note}`, not "delivered".
- A digest is due once the interval has passed since the last digest (or since digest mode was turned on), and at least 2 minutes (`GATHER_MS`) after the oldest held message arrived, so that after a quiet spell a burst still travels together. It is delivered as **one** steered prompt, `[cross-session digest: N routine messages ...]`, with each item framed by sender ID, title, UTC time, entry ID, receipt fields and full text, and the usual peer-not-user footer. A digest carries at most 20 whole messages and 48 KiB for the whole prompt (text, metadata and framing), oldest first (shown with failed, blocked, cancelled or unknown outcomes first, then restricted or unresolved ones); the rest wait for the next interval and are counted in the digest. Nothing is split or summarised. An idle recipient is woken once by it; a busy one takes it at its next step boundary (`metadata.crossSession.digest.woke`).
- Held messages are peer-inbox originals. Before the prompt, a manifest (`peer:batch:…`) records the exact entry IDs, text, SHA-256 and a stable native message ID passed to `ctx.session.prompt`. A returned prompt marks the entries `offered`, not processed. A recipient that cannot be found is a known failure before admission: the same manifest and ID are retried next interval, each retry first durably marked prepared again (if that write fails, it is not attempted), so a crash or lost response during a retry reads back as unknown. A thrown or lost prompt may have been admitted, so the batch becomes `admission_unknown` and is **never resent automatically**; an observed `session.inbox.delivered` for that exact ID and recipient marks it admitted, and `session.inbox.cancelled` makes it terminally cancelled (its entries stay visible in `peer_inbox`, not redelivered). A crash after the manifest is stored reads back as unknown.
- A digest's lookup and native admission run as one step in the recipient's settings queue, so a newer digest choice waits until that admission is decided, and the policy that framed the batch is checked again immediately before the prompt. A batch the current policy no longer allows (for example a turn-off batch after a newer on or unknown choice, including a known failure retried later) is `withdrawn`: never sent, not unknown, and its originals wait for a new batch framed under the current policy with a new native ID. Each manifest records the policy that framed it (reason and interval); a known failure is retried with its ID only under exactly that policy, and a manifest without one (written before this was recorded) never matches. The withdrawal is stored first (after a failed write, only an exact read-back confirms it); until it is confirmed the old batch stays fenced, never relabelled unsent and never replaced by a new attempt.
- **Urgent** messages are delivered at once, on their own. Held and passive messages are not carried with them, and the interval is unchanged.
- A subagent's message to its own parent goes through the relay as before. When the relay delivers it, a parent in digest mode holds a normal one durably (an untyped one as a new original, a typed one by releasing its stored original; if that fails, the relay delivers it as usual) and the relay delivers an urgent one on its own; a typed receipt not taken by the digest is delivered on its own manifest.
- Turning digest mode off delivers one bounded digest of held messages at once; any remainder follows one digest at a time, at least `GATHER_MS` apart. Passive FYI receipts are never delivered by a digest.
- An explicit on/off choice is refused, changing nothing, until storage recovery is complete (each attempt continues recovery by at most one bounded chunk; it never waits for the rest). It is then saved under its session's key, and becomes live only once saved. A session's setting writes (explicit choices and the digest's own timestamp) run one at a time, so an older response never lands over, or clears the outcome of, a newer choice; a later choice waits for the earlier write's outcome. If saving throws, the tool reports the error and reads that key back: a valid saved value (the new choice if the write landed, otherwise the older one) is what stays live; with nothing saved the previous live state stays; if the key cannot be read, or holds anything but `{off: true}` or whole minutes 5–60 with an optional timestamp, the mode is **unknown**. The same validation applies to settings recovered at startup.
- Unknown is never treated as off: `message_digest` reports `digest: "unknown"`, routine messages are held (the sender is told the due time is unknown), nothing held is delivered automatically and no turn-off batch is sent, until a later choice is saved. Urgent messages and native callbacks keep their normal delivery.

State lives in a registry on `globalThis` (`Symbol.for("opencode.opencode-meta.digest.v2")`; v2 because held messages moved to the peer inbox), shared by every copy of the plugin (one per location, plus the copies a reload creates). It is mirrored in plugin storage (`digest:cfg:<session>` and the `peer:` records), which is namespaced by plugin ID and so shared by all copies. Storage is read back once per process (again after a failed read), in chunks of at most 100 scan pages per phase: digest settings, old held records, then the peer inbox. A later operation or tick continues an unfinished recovery from where it stopped, and until every phase completes nothing is delivered automatically and recipient views are refused; a valid saved setting read late still overrides an unpersisted plugin-option default; old `digest:held:` peer messages are imported then as inbox originals under their own IDs, and their old keys are removed only afterwards. Peer-inbox mutations take a per-recipient lock in that registry. Plugin storage has no compare-and-set, so this relies on a single OpenCode server owning the store: a second runtime writing the same storage is unsupported. Each copy ticks every 15 s; a tick is skipped if another copy ran one in the last 10 s, and a digest is claimed synchronously before anything is awaited, so it is delivered exactly once. Unloading only clears the copy's timer: held messages stay for the other or reloaded copies, and nothing on the unload path waits for a delivery (the relay hand-over stays non-blocking too).

**Native completions are not digested.** Subagent and shell completion callbacks keep OpenCode's normal delivery. This plugin registers no synthetic hook and never changes a native wake decision. Peer `send_message` text that looks like a completion is still batched as peer text.

The `digestCompletions` option is deprecated and ignored. Old completion records under `digest:held:`, written only by earlier unpublished builds, are left untouched and reported as `legacy_completion_records`; a fresh install has none.

Retired from v1: `schema`, `todo_packets`, `database_info` — v2 exposes no database or todo table to plugins.

The tool is registered with `codemode: false` so it appears directly in the model's tool list. The `[recall-nudge]` system text now lives in `opencode-recall-lite`; install both plugins together (this one imports the shared index module by relative path).

Options: `"debug": true` logs registration to the server log; `"digestSessions"` as above. `"digestCompletions"` is retained only as a deprecated, ignored compatibility option.

Tests: `bun test` in this directory (mocked v2 context).
